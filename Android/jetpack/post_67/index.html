Datastore是什么

从Library的介绍可以得到以下信息：

Store data asynchronously, consistently, and transactionally, overcoming some of the drawbacks of SharedPreferences

以异步、一致和事务性存储数据，克服了 SharedPreferences 的 一些缺陷 。

这样的信息还是太宽泛了，继续探索官方内容，可以得到更进一步地描述：

DataStore provides a safe and durable way to store small amounts of data, such as preferences and application state.

It does not support partial updates: if any field is modified, the whole object will be serialized and persisted to disk.

If you want partial updates, consider the Room API (SQLite).

Datastore 提供一种安全持久的方式 存储少量数据 ，例如首选项、应用状态。 它不支持局部更新，一旦任意字段被修改，整个对象都会被序列化并持久化写入磁盘。

如果需要局部更新的特性，考虑使用ROOM（底层是SQLite数据库）

为什么需要使用Datastore

读者诸君不要觉得该提问很无礼，我们每一次技术决策都是面对同类问题

回答此类问题，存在方法论。在Datastore上，需要考虑以下几点：

  • 项目中是否存在轻量化存储需求
  • 建立方案评估维度
  • 其他方案有哪些，其他方案被排除、次选

相比SharedPreferences的改进

DataStore 提供ACID保障，线程安全，为无阻塞设计。

针对SP的设计缺陷，做出改进，SP的部分设计缺陷：

  • 同步API违背严格模式
  • apply()、commit() 没有错误信号机制
  • apply() 会在fsync()阶段阻塞UI线程
  • 非持久性，有几率返回未被持久化的状态
  • 无一致性或事务语义
  • 解析错误会抛出运行时异常
  • 暴露内部状态对应的可变引用

相比SQLite的技术特性

SQLite作为数据库，适合存储结构化数据，而首选项等对应的数据模型，即使设置项很多，也可以设计成宽表。 而且可以设计成支持设置回溯（例如仅新增不修改，或者增加日志表），修改时可以局部修改。

数据库天然支持ACID特性，但需要注意多进程并发写时的写锁。

Datastore 可以按照键值对形式或者对象存储形式使用，但不支持局部更新，因此，当需要存储的field非常多时，不推荐使用

相比于三方库，如MMKV

微信的MMKV，需要注意，它有相当典型的业务背景特色，印象中在18年微信某个大版本更新后，出现了一股”使用特定字符串让微信崩溃”的热潮。

当时微信已具备亿级用户群，迫切需要一套解决方案监测此类线上问题，不难理解，其技术要求应当包含：

  • 避免受到进程崩溃影响
  • 处理速度快

持久性的重要度倒在其次，因此，业务场景中对数据丢失有较高容忍度时可考虑使用

使用方式

Google提供两种不同的DataStore实现：Preferences DataStore 和 Proto DataStore：

  • Preferences DataStore ：键值对风格，使用键存储和访问数据。不需要预定义的架构，也不确保类型安全。
  • Proto DataStore ：对象存储风格，将数据作为自定义数据类型的实例进行存储。要求使用 Protocol Buffers 定义架构，可以确保类型安全。
